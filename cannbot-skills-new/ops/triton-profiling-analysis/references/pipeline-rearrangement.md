# 流水重排（理论流水排布）

> 来源：profiling 方案（用户提供）。消气泡的兜底手段：当代码结构决定了计算块
> 之间只能串行、掩盖无法成立时，靠双缓冲/并行度修不动，需要重排流水。

## 触发时机

- 气泡消除尝试 **10 次**后仍未达成 bound（某 pipe 占比超 50%）→ 取当前占比
  靠前的 pipe 优化，**或尝试重排流水**；
- 仿真气泡分析显示主要空泡是 V_C 掩盖失效 / CV 阻塞等**结构性**问题
  （依赖关系导致无法并行）→ 直接进入重排评估。

## 方法（三步）

### 1. 列计算块，标注执行单元

根据阶段 2 计算草图（sketch）确定计算的依赖关系：

- 分析主要有哪几块计算；
- 每块标注执行单元——**cube**（mm / 点积类收缩计算）或 **vector**
  （softmax / topk / 元素变换 / 归约类）。

### 2. 建依赖图

分析不同计算块之间的依赖关系，画出依赖图。

示例（attention 类算子）：

```
1. Sel = topk(si)        → vector
2. S   = mm(q, k)        → cube
3. P   = softmax(S, sel) → vector
4. O   = mm(P, V)        → cube

计算依赖图：1, 2 → 3 → 4        （1 与 2 无依赖，可并行）
```

### 3. 结合实测数据排布流水

分析实测的性能数据如何排布流水：

- **无依赖的计算块并行排布**：如上例 1（vector）与 2（cube）可同时发射，
  互相掩盖——目标是让 C 流水与 V 流水重叠（对照仿真掩盖矩阵）；
- **有依赖的计算块串行排布**：如 3 必须等 1、2 完成，4 必须等 3——串行链上
  的每块都是潜在 bound，块内优化优先；
- 用上板占比验证排布假设：若实测 cube pipe 占比远低于理论计算量占比，说明
  cube 在等数据（掩盖失效），印证依赖排布问题而非算力不足。

## 约束

- 重排是**代码结构级改动**（计算块拆分/顺序调整/grid 重排/融合），本 skill 只
  给排布方案与证据，落地交主 agent / `triton-latency-optimizer`；
- 重排后必须重新走「上板判 bound」：bound 大概率转移，旧结论全部作废；
- 依赖图来自 sketch 与代码事实，禁止凭空猜测计算块归属（cube/vector 以实际
  发射的指令类型为准，可用仿真 CSV 的 pipe 归属佐证）。
