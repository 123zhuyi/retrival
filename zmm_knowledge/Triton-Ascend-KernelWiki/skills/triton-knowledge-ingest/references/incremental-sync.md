# 批次级增量同步 pipeline（路由 2）

同一 source 推进新批次（新一批轨迹、文档仓新 commit 区间）时走本流程。

## 0. 读 watermark，定范围

- 从内容根 `index.md` frontmatter 读上次 pin（`trajectory_commit` / `upstream_commit`）。
- **没有记录 watermark、或它不是可解析的 sha/批次号 → 停下向用户索取起始基线，不要用 `HEAD~N`/最近 tag 猜**（对齐目标知识库根目录的 `log/README.md`，占位）。
- 文档仓：`git diff --stat <旧sha>..<新sha>` 出文件级清单；轨迹集：按批次时间/目录清单算增量。

## 1. 算增量 / 归三类

逐块看 diff/新增轨迹，归三类：**新增实体 / 变更实体 / 受影响的既有卡**。

- commit/批次编号只作发现机制 + 溯源锚点，不作分批依据。
- 采集**意图溯源**（任务描述、算子名、报错主题）——进相应卡的溯源，不进知识正文。

## 2. 逐实体走原子动作

按编排器 §3.1 五步走（理解源 → 影响分析 → 建/更新卡 → 交叉链接 → 三件套），委派对应分类生产 skill 执行。

- **更新既有卡前先读它现在写了什么，在其上增量补充，绝不整体覆盖**。
- runbook 已有同类条目 → 只 append「已知实例」反链（干净上下文子 Agent 合并）。
- 轨迹中的失败迭代 → 评估是否沉淀为 `AP-*` / `CT-*`；同主题已有点位 → 补充失效边界。

## 3. 收尾

同 new-source-onboarding §4（index → 检索重建 → 图谱增量 → 覆盖账 → verify → 日志 → **推进 watermark**）。

- **watermark 推进前必须完成所有卡写入 + verify + 图谱 + 日志**；它是唯一"已落地"开关。
