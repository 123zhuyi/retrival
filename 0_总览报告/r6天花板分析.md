# MhcSinkhorn 理论上限分析（放弃当前实现后的纯讨论）

> 数据基础：v12 实测（官方 73.80）+ 本仓全部 profiling 证据链 + hicann/ops-transformer 官方源码 +
> Ascend950PR_9579 实测规格（56 vec 核 @1.65GHz、128 fp32 lane/核/拍、HBM V 侧 ~1.48TB/s、UB 248KB/核）。
> 计分口径：SOL = (T_base − T_HW) / ((T_cand − T_HW) + (T_base − T_HW))，性能分 = 50 × mean(SOL)。

## 0. 先回答"100 分为什么物理不可达"

T_HW 是 bench 标定的"硬件理论时间"，本算子 20 个 case 里 18 个 = **1.0µs**（case6 = 1.59µs、case12 = 1.55µs）。
SOL = 1.0 当且仅当 **T_cand = T_HW**。而 1.0µs 大致是一次 kernel 启动+最小访存的硬件地板
（实测：case4 纯连续读写一遍 128KB 的 `_k_merged_io` = 2.10µs；最小 case18 的完整计算也有 3.91µs）。
一个要做 20 轮迭代的真实算子不可能压在 1µs——**100 分要求 T_cand ≤ 发射地板，物理不可达**。
SOL 公式还是饱和型的：T_cand 从 8µs 压到 4µs，SOL 只从 0.53 涨到 0.75；越接近 T_HW 收益越平。

## 1. 三块地板（每 case 的下限 = 三者合成）

| 地板 | 内容 | 量级 |
|---|---|---|
| **F1 发射+访存** | kernel 启动 ~1µs + 数据进出一趟（2·B·n²·4B，迭代全程驻留 UB，无重复 GM 往返） | case4：1.09µs；case6/12：2.4µs；小 case ≈ 1µs |
| **F2 吞吐** | 每矩阵每轮 ≈ 4n² lane-op（行加 n² + 行除 n² + 列加 n² + 列除 n²），20 轮 + 首轮 softmax；按 7168 lane × 1.65GHz、50% lane 利用率折 | case4：0.23µs；case6/12：3.6µs；case11：2.0µs |
| **F3 迭代链延迟** | 20 轮严格串行（行归一 → 列归一依赖链），每轮链长 = 归约+除法+归约+除法；**与 B 无关，只随 iter 线性**。理想归约（单指令级）~150 拍/轮，工程级 ~300 拍/轮 | iter=20：1.8µs（乐观）/ 3.6µs（保守）；iter=40 翻倍 |

**关键洞察：这个算子在 bench 口径下不是带宽题，是"延迟链 × 归约原语效率"题。**
F1 和 F2 在大多数 case 上是零头；F3（链延迟）和"归约的指令级成本"才是主项。

## 2. 天花板数值（脚本核算，逐 case 见文末附表）

| 情景 | mean SOL | 总分上限 |
|---|---|---|
| 物理 100 分 | 1.000 | 100 —— **不可达**（要求 T_cand = 发射地板） |
| 乐观天花板（单指令归约 + 150 拍/轮链 + 完美掩盖） | 0.785 | **≈ 89** |
| 保守天花板（AscendC 手写工程级，300 拍/轮链） | 0.675 | **≈ 84** |
| **Triton 表达力天花板**（归约只能走 tl.sum/显式展开，无单指令块归约） | ~0.55~0.60 | **≈ 78~80**（估） |
| **当前 v12（Triton）** | 0.476 | **73.80** |

佐证"保守天花板"的现实性：当前 v12 有 3 个 case 已超过保守模型的理想值（case18 实测 3.91µs < 模型 4.6µs——
B=1 单核窄向量的链延迟比模型短），说明 84 并非遥不可及的空想上界，而是 AscendC 手写可达到的工程线。

## 3. 差距分布：钱花在哪

按"当前 SOL 距乐观天花板"的损失排序（损失 = SOL_理想 − SOL_v12，乐观口径）：

| 梯队 | case | 损失源 | 性质 |
|---|---|---|---|
| 大 n（10/11/12） | 0.52~0.59/case | **每轮 n 次行归约的跨 lane 税**（tl.sum 落成 reduce 树 + temp_buffer 重排；单轮实测 0.94~1.94µs vs 单指令 ~0.05µs） | **Triton 表达力硬伤**——官方用 `ReduceSumWithDataBlock` + `DIST_E2B_B32` 各一条指令 |
| 大 B（5/6） | 0.30~0.41/case | 16 路 stride-gather load（MTE2 46%）+ 2.29 波尾波 | gather 已是 Triton 最优形态（merged/split 加载实测证伪）；官方用单指令 `DataCopyGather` |
| 中 B n=4（3/4/14~20） | 0.22~0.33/case | 链延迟未充分掩盖 + 每 program 固定开销 | Triton 内还有小空间（~1-2µs/case），但很贵 |
| 小 case（1/2/13/18） | 0.13~0.31/case | 已贴近发射地板 | 几乎无空间 |

## 4. 剩余杠杆的价值量（总分增量估算）

| 杠杆 | 预期增量 | 代价/风险 |
|---|---|---|
| **AscendC 重写大 n 路径**（n=8/12/16 用 Reg::ReduceSumWithDataBlock + DataCopyGather/Scatter 复刻官方） | case10/11/12 SOL 0.25/0.18/0.21 → 0.5~0.6 区，**总分 +4~7** | 脱离 Triton 技术栈；工作量最大 |
| **提前收敛截断**（iter 20→6，F3 ×0.3） | 乐观模型下 **总分 +3~5** | 偏离 iter_step 固定轮数语义；官方 kernel 也没做（其 README 的收敛阈值在 kernel 里未实现）；容差余量薄（最差 matched 0.994 vs 0.99） |
| Triton 内继续打磨（链延迟掩盖、调度） | +0.5~1 | 已接近 Triton 天花板 78~80 的下沿 |

## 5. 结论

1. **100 不可达**（发射地板），**物理极限 ≈ 89**（理想）/ **84**（工程），**Triton 极限 ≈ 78~80**。
2. 当前 73.80 已拿到 Triton 极限的 ~93%；剩余 Triton 空间只值 ~4~6 分且单价越来越高。
3. 要过 80 必须换技术栈（AscendC 复刻官方归约原语）或换语义（提前收敛）——两者都是方向决策，不是调优。
