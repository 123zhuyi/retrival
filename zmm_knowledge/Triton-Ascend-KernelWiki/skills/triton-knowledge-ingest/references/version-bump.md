# 大版本升级 pipeline（路由 3，摘要）

> 权威流程见目标知识库根目录的 `SPEC-Version-update.md`（占位，后续补充）。本文件只给摘要与分流原则。

## 触发

triton-ascend 版本切换（如 3.x → 4.x），可能伴随 API 语义变化、IR 变化、编译器行为变化、平台支持矩阵变化。

## 流程概要

1. **双 pin diff**：旧版本 pin 与新版本 pin 各取一份文档/接口清单，做 diff。
2. **5 类分流**（逐项判定）：
   - **新增**：新版本新增的 API/特性 → 对应分类 skill 建新卡。
   - **变更**：语义/签名变化 → 更新既有卡（增量补充 + 标版本适用条件，不整体覆盖）。
   - **失效**：被移除/不再推荐 → 标 `deprecated`，写明替代关系。
   - **行为漂移**：同名 API 行为变化（精度/对齐/默认值）→ `> ⚠️ 矛盾标记` 并存 + 版本边界。
   - **不受影响**：确认无变化即可，不动卡。
3. **版本迁移沉淀**：架构性变更（如某优化点在新版本失效/变成默认行为）由编排器沉淀到 `runbooks/<对应分类>/` 的版本迁移条目（`dimension` 标原分类，正文写清新旧版本行为差异与迁移动作）。
4. **受影响条目全量复核**：凡 frontmatter/正文引用被变更 API 的卡，逐张复核并记录。
5. **finalize-version-bump 原子推进 watermark**：全部分流完成 + verify + 图谱 + 日志后，一次性推进 pin。

## 红线

- watermark 推进是原子的：要么全部完成，要么不推进。
- 版本差异、平台差异不能互相覆盖，必须写清适用条件。
- 失效知识不静默删除：`deprecated`/`retracted` + 替代关系；优先沉淀为负知识。
