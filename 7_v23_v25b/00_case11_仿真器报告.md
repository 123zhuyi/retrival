## 5. 结论：case11 的时间构成（仿真实锤版）

```
18.4µs ≈ prologue 装载（~2µs，12 路跨步 load）
       + softmax 首轮（~2µs）
       + 5 轮迭代（~7µs，RVECLP 主导 85% 有效）
       + epilogue 写回（~6-8µs，12 路 join store 串行，与计算几乎零掩盖）
```

**最大单发现：join store 写回相位占 ~1/3 时间且与计算完全串行**（VEC←MTE3 等待 8.25µs + MTE3 27% 活跃）。join 合并 store（v10 的收益来源）在截断后成为最大固定开销项；12 路 `o_r` 计算+写回彼此独立却只走 MTE3 一条管。

## 6. 可优化性评估

| 方向 | 可行性 |
|---|---|
| store 与末轮计算掩盖 | 数学不可行（全部 o_r 依赖最终 cv，而 cv 依赖全部行）——但 12 路 store 间的并行化已在（MTE3 带宽受限，27% 活跃 10.3% eff） |
| 减少 store 量（更窄 join 树/直接 16 路 store） | v10 已对比过：join16 合并优于 16 路 strided store（当时 -30%）——保持 |
| store 与下一 case 的装载掩盖 | 多 case 流水（生产场景才有意义，bench 单算子无） |
| **AscendC** | DataCopyScatter 单指令写回 + 寄存器常驻免 staging——剩余唯一大招 |

**判定：case11 在 v25b 形态下的 18.4µs 构成 = 1/3 装载 + 2/5 迭代 + 1/3 写回，三段全部有板/仿真证据，无 Triton 内剩余空间。**
