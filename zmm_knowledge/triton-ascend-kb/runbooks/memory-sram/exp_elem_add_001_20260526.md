## Add算子块大小动态调整优化经验

【优化维度】：访存效率
【泛化层级】：条件性（迁移条件：硬件 910b2, 910b3，fp32/fp16/bf16 的逐元素二元运算（含广播与标量 alpha）；失效边界：含多次中间张量读写的复合算子单一档位不够，需更精细的调优策略；分档阈值（1024/8192）按 910B2 向量单元标定，核数/UB 容量不同的硬件需重新标定）

### 原则
- 小张量使用过大的块大小会导致资源浪费和效率低下
- 根据张量大小动态调整块大小可优化资源利用率
- 在Ascend910B2硬件上，合适的块大小直接影响向量单元利用率
- 性能提升：从1.7890x加速比提升至2.1456x
- 适用场景：各种规模的elementwise add操作
- 验证案例：50个测试case全部通过

### 代码/骨架出处
- `python`:
```python
# 根据元素数量动态选择块大小
if n_elements < 1024:
    blockSize = min(512, triton.next_power_of_2(n_elements))
elif n_elements < 8192:
    blockSize = 1024
else:
    blockSize = 2048
```

**坏实践（反例）**：所有规模固定一个块大小
```python
BLOCK_SIZE = 2048                                    # 一刀切
grid = (triton.cdiv(n_elements, BLOCK_SIZE),)        # n=512 时仅 1 个 program，大量 lane 空转
```
后果：小张量下向量单元利用率低，加速比只有 1.7890x。✅ 正解：按 n_elements 分档（<1024 取 min(512, next_power_of_2(n))，<8192 取 1024，否则 2048），加速比提升至 2.1456x。

**已知实例**：elementwise §raw (`experiences/elementwise/exp_elem_add_001_20260526.yaml`)
- 声称性能收益：从1.7890x加速比提升至2.1456x
- 备注：- 此优化对简单的elementwise操作效果显著 - 对于复杂的复合操作，可能需要更精细的调优策略
