## 一、口径校验：launch/call

`launch/call` 若 > 1，说明该 kernel 在一次 forward 内发射多次、被口径低估。

## 二、优化版资源画像（主导耗时 case，累计 80%）

```

串行度 (aicore_time + aiv_time) / Duration = 1.6610   > 1.5 -> Cube-Vector 串行
```

结论：
- `aic_mac_ratio` 仅 9.9%，Cube 乘加不是瓶颈；块稀疏把 GEMM 打碎成 128×128 的小块，
  单块 MAC 时间远小于调度/同步开销。
- `aic_scalar_ratio` 48.5% 配合串行度 1.66，指向**同步等待被计入标量管线**，
  而不是"标量运算过多"。要下标量退化结论必须先 dump IR 确认。
- 剩余优化空间在 CV 流水与同步结构（循环嵌套层数、set_flag/wait_flag/pipe_barrier 数量），
  不在访存也不在算力。

## 三、framework 侧耗时构成

```
aclnnRepeatInterleaveIntWithDim_RepeatInterleaveV2   325.39 ms   97.91%
aclnnSoftmax_SoftmaxAiCore_SoftmaxV2                   1.83 ms    0.55%
aclnnBatchMatMul_BatchMatMulNd_BatchMatMulV2           1.54 ms    0.46%
（其余 20+ 算子合计 < 1.1%）
```

参考实现每个 batch 都做 `k[ks:ke].float().repeat_interleave(G, dim=1)`，
物化一份 `[sk, H, D]` 的 fp32 K/V —— 这一步占了 framework 侧 97.9%。
Triton 侧按 `hk = h*HK//H` 直接取 K/V，不需要这次物化。
