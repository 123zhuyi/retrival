# 双资源审计：搬运 × 计算，量 × 速度（Unified Resource Audit）

适用场景：已取得同一 OPPROF 的 `OpBasicInfo.csv` + `Memory.csv` + `PipeUtilization.csv` + `ArithmeticUtilization.csv`（+ `L2Cache.csv`），且有 `last_pass.mlir` 与任务形状参数时，按一条流水线完成**四象限对账**：

| | 量（volume） | 速度（rate） |
|---|---|---|
| **搬运** | 语义字节 vs CSV 通道计数（S1-S4） | 通道字节÷pipe忙时 vs pipe 理论带宽 → 效率比（S5） |
| **计算** | 语义 FLOP vs 指令数×分形片（S7） | 程序 FLOP÷忙时 vs chip_spec 峰值 → 忙时 MFU（S7） |

配套字段语义见 `profiling.md` 的「Memory.csv 数据通路字段表」。

### 统一判定门（全程有效）

1. 单次发射确认；2. 计数闭合（指令数=IR 调用点数；发送≈接收）；3. 归账闭合 ≤±5%；4. 同币种（FLOP 与峰值同分形片单位）；5. 时长不跨 CSV、fops/estimate 列不采信；6. 悬置项显式列出，禁止硬凑闭合。

## 架构准则（A3，用户给定，优先级最高）

**A3 机器上 Cube 与 Vector 子核之间没有数据通路；任何跨子核数据交换必须经 GM 中转。**

推论（分析时强制适用）：
1. 跨核中间量的 GM 往返是**架构必要**，不计入冗余；冗余只判三类：**同方向重复搬入、超必要宽度（f32 当 bf16 可用）、可被调度消除的交换**
2. 理想量分层：L0 纯数学下限（无视 A3）→ L1 A3 架构理想（每变量每方向恰过一次、最窄宽度、最优调度）→ 实测。膨胀判定对齐 L1，不再对齐 L0
3. **常驻判定**（逐变量必答）：变量能否驻留在消费者核的片上（UB/L0C/L1），避免再次搬入；不可核内常驻时，能否 L2 常驻（多 program 共享同一数据经 L2 捕获）

## 前置检查（不通过禁止下结论）

1. **单次发射确认**：OpBasicInfo.csv 恰 1 行（多发射必须先归一化）
2. **核数确认**：cube 核数 = Block Dim，vec 核数 = Mix Block Dim（c1 例：16/32）
3. **迭代数确认**：从源码主循环 `range(NT)` 与 shape 推 NT（c1 例：⌈612/64⌉=10）
4. **CSV 间时长不可混用**：同 OPPROF 各 CSV 报的时长互不相同（分指标组多 pass），字节÷忙时只在同一 CSV 内做

## S1 理想通路量（变量级）

**规则**：每输入元素恰读一次、每输出元素恰写一次、**中间量为 0**（理想实现中间量不出片上）。

步骤：
1. 列任务全部输入/输出张量：`字节数 = Π(形状) × dtype 大小`
2. 通道归属（语义字节 × 结构归属，两处知识来源要分开记）：
   - dot 操作数类输入 → **GM→L1**（MMA 路径）
   - 逐元素类输入 → **GM→UB**（vector 路径）
   - 全部输出 → **UB→GM**
   - 中间量 → **L0C→GM = 0**
3. 产出变量×通道理想量表。

GDN c1 例（MB）：

| 变量 | 字节 | 通道 | 理想量 |
|---|---|---|---|
| k [1,4,612,128]bf16 | 0.63 | GM→L1 | 0.63 |
| w [1,8,612,128]bf16 | 1.25 | GM→L1 | 1.25 |
| g [1,8,612]f32 | 0.02 | GM→UB | 0.02 |
| hi [1,8,128,128]bf16 | 0.26 | GM→L1 | 0.26 |
| u [1,8,612,128]bf16 | 1.25 | GM→UB | 1.25 |
| v_new / h / ht | 1.25/2.62/0.26 | UB→GM | 4.13 |
| （全部中间量） | — | L0C→GM | **0** |
| **合计** | | | **读 3.41 / 写 4.13** |

⚠️ 纯语义不知道通道——按通道的理想量是「语义字节 × 结构归属」混合口径，须标注。

## S3 逐变量归账（实测 → 变量）

从 last_pass.mlir 按函数节提取搬运调用点，机械求和：
`变量流量 = site 单次字节 × 迭代数 × program/核数`。

| 节 | 调用前缀 | 含义 |
|---|---|---|
| mix_aic | `nd2nz` / `set_l1_2d` | GM→L1 读（后者仅布局配置不取数）/ L1 内操作 |
| mix_aiv | `load_gm_to_ubuf_{1d,2d}_*` | GM→UB 读（f32 版 = 中间量读回） |

## S4 冗余判定（为什么实际 > 理想）

三类冗余模板，逐变量套用：

| 类型 | 判定特征 | 冗余公式 |
|---|---|---|
| A. 同方向重复搬入 | 变量被多个 program / 多个迭代重复读入（grid 复制：GQA 头共享 / v-block 拆分等） | 理想量 × (搬入次数 − 1)；逐变量必答「可否常驻」：核内（数据段相同才可）→ L2（相邻调度可捕获）→ 不可 |
| B. 跨核交换超必要（A3 准则下交换本身架构必要，非冗余） | IR 证据 = mix_aic/mix_aiv 节读回点 + fixpipe@gm；冗余只判三种：**同方向重复搬入 / 超必要宽度（f32 当 bf16 可用）/ 调度可消除的交换**（换核内驻留或换侧合成即可免） | 超宽 = (f32 字节 − bf16 字节) × 次数；可消除交换 = 该交换字节（调度改写后归零） |
| C. 接口计费 | 整行写变量不放大 vs 半行写变量 ≈2×（同发射内自然对照） | 逻辑量 × (计费行宽/逻辑行宽 − 1) |

**逐变量必答三问（报告输出格式）**：是否重复搬入？为什么？可否常驻（核内/L2/不可）？

**A 类的 IR 形式化证明（地址依赖分析法，2026-10-26 GDN 定案）**：
单节 IR 即可证明跨 program 重复读，无需跨 program 对比。步骤：
1. 提取 `get_block_idx` 后的 pid 分解算式（divsi/remsi 链），标注每个 program-id 分量（n/vh/iv…）
2. 追读点 `subview → reinterpret_cast → affine.apply → 算式链`，收集地址算式引用的 pid 分量集合
3. **判定**：地址依赖集合不含某拆分分量（如 iv）→ grid 沿该维度的 program 全部读同一地址 → 重复次数 = grid 规模 ÷ 地址流条数。最强证据形态 = **该分量变量在整节中根本不存在**（编译器已消除，GDN 例：mix_aic 全函数无 `remsi %c2`，iv 被完全消除）
4. GDN 定案示例：k 地址 = f(vh/2, i_t)（L46 `divsi %7,2` = GQA 折叠）→ 16 programs / 4 地址流 = ×4；w 地址 = f(vh, i_t) → 16/8 = ×2
注意区分：**循环内每迭代读点（地址含 i_t）读不同数据，非重复**；**同地址被多 program 读 = 跨 program 重复（真冗余）**；**每迭代读同位置但数据已被对方更新（h workspace）= 拆核必要交换，冗余在"调度可消除"而非"重复读"**。

**GDN c1 全读点统计定案（IR 地址依赖 + workspace 布局破译）**：
workspace 每 program 私有槽 73,760B（#map1/8/9/10：`pid×73760` + 区域偏移：h@0、dot1@16416、v_dec@32800、dot2@40992）——4 个 workspace 读点全部 pid 私有，无跨 program 重叠。pid 分量存在性：**cube 节无 iv 变量（无 `remsi %c2`），vec 节有 iv（L43）且 u 地址引用之（%13→%26→%57）；vec 拆分另有 get_sub_block_idx（L30-35，子核行拆分 ×32/×64）**。

|---|---|---|---|---|---|---|
| w | cube L96 | 是 | vh, i_t | 8 | **×2** | iv 不进地址（cube 节无 iv） |

**S4.5 IR 重复读入统计标准流程（可复现，配套通用脚本 `scripts/ir_read_duplication_audit.py`）**

```bash
# 通用：任意 last_pass.mlir 任意函数节；不预设算子/拆分数/操作名
python3 scripts/ir_read_duplication_audit.py <last_pass.mlir> <节名> \
    [--ops nd2nz,load_gm_to_ubuf] \
    [--hints hints.json]   # hints: {"arg_names":{"%arg3":"k"}, "program_count":16} 可选
```

脚本自动产出：签名入参表（workspace/输出标记来自属性、死输入=仅签名引用）→ pid/子核分解算式区（取模=拆分维度候选，**不预设除数**）→ 每个调用点**逐 memref 操作数**的根入参追溯 + 循环位置 + 地址链展开 → workspace 视图槽（按 arg_type 属性识别）→ affine_map 定义体。无任何算子专属假设：操作名白名单、拆分常量、GM 侧操作数位置均不硬编码。

拿到脚本证据后，分析者按五步完成判定：

1. **命名**：入参→张量，用使用方式排除法（mma 操作数必被 cube 读 / 逐元素输入被 vec 读 / 全节仅签名引用 = 死输入）
2. **判依赖集合**：从地址链收集 pid 分量 + i_t；**最强证据 = 分量变量整节不存在**（编译器已消除，如 GDN cube 节无 iv）
3. **算流数**：依赖集合能区分几类 program → 地址流条数；重复次数 = program 总数 ÷ 流数
4. **分类**：跨 program 同地址 = 真重复（A 类）；workspace 槽（偏移含 pid，私有）每迭代新数据 = 交换（B 类，非重复）；地址含 i_t = 迭代新数据（正常）
5. **对账门**：IR 结构倍数 vs 板端实测比值 ≤ 1.05 才采信；不闭合回查 affine map 解码与半行计费

**IR def-use 追溯定名表（2026-10-26，回答"哪些读点读哪个张量"）**：mix_aic 四读点 = L96/L114 读 %arg3/%arg5（k/w，循环内每迭代）+ **L73 读 workspace（h 回读，实锤）+ L145 读 workspace（v_dec，实锤）**；mix_aiv 四读点 = L171 读 %arg7（g）+ L246 读 %arg6（u）+ L267/L342 读 workspace（dot1/dot2 读回）。**意外发现：hi（%arg4）在该编译产物中全程未被读**（与源码 `b_h += hi` 矛盾，两种解释：该采集 dispatch 走了 use_init=False 占位分支，或入参映射仍有缺口）——理想量表中 hi 0.26MB 应标注「条件项：USE_INITIAL_STATE=true 时才存在」，采集态实测 hi 流量 = 0。

## S5 通路搬运效率比

1. **实测速度** = 通道字节/核 ÷ 该 pipe 忙时/核（PipeUtilization 对应字段：GM→L1→`aic_mte2_time`；GM→UB→`aiv_mte2_time`；L0C→GM→`aic_fixpipe_time`；UB→GM→`aiv_mte3_time`）
2. **理论速率**取值顺序：**chip_spec pipe 端口带宽（正式口径）** → 无文档时才退回最快同类 pipe 实测做经验上限（标注）。GM 侧搬运的 spec 锚 = **L2读 198 / L2写 154.8 GB/s/核**（Ascend910_9372；DDR 侧仅 57.6）
3. **效率比** = 实测速度 / 理论速率；与 pipe 忙时占比联读——占比 <50% 说明非该 pipe bound，效率低 + 占比低 = 小片化传输问题而非带宽不足

GDN c1 例（经验上限 = cube MTE2 82.4 GB/s，大块连续 tile 传输）：

| 通路 | 实测速度 | 效率比 | 忙时占比 | 诊断 |
|---|---|---|---|---|
| GM→L1 | 82.4 GB/s | 1.00（基准） | 13.6% | 整 tile nd2nz，效率基准 |
| L0C→GM | 76.0 GB/s | 0.92 | 12.2% | fixpipe 突发，接近基准 |
| GM→UB | 30.7 GB/s | 0.37 | 18.2% | 2D 跨步小片，效率受损 |
| UB→GM | 22.1 GB/s | 0.27 | 21.7% | [32,64] 子 tile 半行写，最慢 |

规律：**同架构下大块连续传输 ≈ 1.0，小片跨步 ≈ 0.3**——提升 vec 侧效率的方向是加大传输片粒度/对齐行宽，而非换 pipe。

**板上实证链与 spec 对账（2026-10-26 升级）**：
效率比的分子（通道字节，Memory.csv）与分母（pipe 忙时，PipeUtilization.csv）**均为板端计数器**，非模型推算。官方 `active_bw` 列独立互证：L0C→GM（72.2 vs 我算 76.0）、GM→UB（29.0 vs 30.7）、UB→GM（20.9 vs 22.1）三者差 <5%；**唯 cube MTE2 差 3.3×**（官方 24.6 vs 我算 82.4）——L2 miss 过滤假说方向吻合（580KB×21% miss=121KB→16.8 GB/s）但不精确闭合，**标注悬置**，不影响排序。
spec 效率比（正式口径，L2 端口）：

| 通路 | 实测 | spec(L2 端口) | 效率比 | 经验上限比（次口径） |
|---|---|---|---|---|
| GM→L1 | 82.4 GB/s | 198.0（L2读） | **41.6%** | 1.00 |
| L0C→GM | 76.0 GB/s | 154.8（L2写） | **49.1%** | 0.92 |
| GM→UB | 30.7 GB/s | 198.0（L2读） | **15.5%** | 0.37 |
| UB→GM | 22.1 GB/s | 154.8（L2写） | **14.3%** | 0.27 |

四通道全部 ≤ spec 的 50%——搬运不仅非 bound，连最快的通道也有一倍以上 spec 余量。

## S6 审计 → 草图修改建议（闭环）

冗余类型映射到草图缺失的预算约束（GDN c1 为动机案例）：

| 冗余类型 | 根因 | 草图应补的约束 |
|---|---|---|
| B 拆核协作 | 草图只写"算什么"，未规定跨核交接方式与宽度 | ① 流量表显式加「跨核中间量 = Σ(字节 × 迭代 × 2 方向)」；② 交接 dtype = 消费者所需最窄宽度（bf16 优于 f32）；③ 草图阶段评估全 vec / 全 cube / mix 三形态的交接总成本，逐元素量小则避免 mix |
| A grid 复制 | 拆分了被多 program 共享的维度，无读放大预算 | ① 每输入张量标注「共享 program 数 = 沿共享维度的拆分数乘积」；② 拆维选择规则：优先拆非共享维度（batch/head），拆共享维度（K/V 相关）须过「读放大 vs UB 容量/并行度」权衡；③ 共享同一大张量的 program 排相邻 grid 位置（提高 L2 空间局部性捕获） |
| 状态回读（悬置类） | 状态累加器驻留策略未声明 | 草图显式声明「状态量驻留在产生它的核，落盘仅为输出副本」 |
| C 接口计费 | 落盘 tile 行宽未约束 | 落盘形状行宽 ≥ 缓存行（≥128B，如 [64,64]bf16 及以上），禁止 <行宽 的子 tile 落盘 |

草图模板增量（写进 sketch.txt 的流量预算节）：**三类预算行 = 跨核中间量 / 读放大系数表 / 落盘行宽声明**。审计发现超预算 → 回写草图对应约束，而不是只在代码层打补丁。

## S7 计算量审计（与搬运审计 S1-S5 对称）

三层口径，与搬运侧对齐：

| 层 | 来源 | 产出 |
|---|---|---|
| 理论计算量 | 算子数学：每个语义 dot `2×M×N×K` + 逐元素 op 计数 | 理论 FLOP |
| 结构计算量 | IR MMA 调用点：调用数 × cbuf 视图形状解码（`8x4x16x16` 片布局→`[128,64]` 等逻辑形状）× 迭代 × 程序数 | 结构 FLOP |
| 实测计算 | **ArithmeticUtilization.csv**：`aic_cube_fp_instr_number`（执行的 MMA 计数）+ `aic_cube_fp16_ratio`；PipeUtilization：`aic_cube_time`（忙时） | 执行指令数 → 分形片换算实际 FLOP |

**ArithmeticUtilization.csv 字段与换算陷阱（2026-10-26 定案）**：
- `aic_cube_fp_instr_number` = 每核执行的 MMA **tile 级**调用计数（GDN：20 = 2 调用点 × 10 迭代，与 IR 精确闭合）
- ⚠️ `aic_cube_fops` 列**不能直接采信**：它把每条计数指令当 1 个 16×16×16 分形片（8192 FLOP）；而每个 tile 调用实际展开 = (M/16)×(N/16)×(K/16) 片（GDN dot1 = 4×4×8 = 128 片），**低估 128×**（2.62 vs 335.5 MFLOP）
- 正确换算：**实际 FLOP = instr 数 × Σ(每调用点片数) × 8192**；片数从 IR cbuf 视图形状取
- `fp16_ratio` 是"占全程周期比"，与忙时占比同量级 ≠ 工作类型占比
- 向量侧 `aiv_vec_fops` 按操作计数（Σ 10.1M，与逐元素清单同量级），可信度高于 cube fops 列

判定规则：
1. **计算冗余判定**：结构/理论 = 1.00 为期望值；>1 说明编译器插入了额外计算（重复 MMA、多余 cast/转换）。与搬运侧不同，**grid 拆分不产生计算重复**——计算按输出划分，每个 program 只算自己的输出半片；输入共享（k ×4）只放大搬运，不放大计算
2. **饱和判定**：忙时占比 <50% → 计算非 bound；等效忙时算力 vs 峰值（MFU）需 peak 标定，仅 mfu 模式做（`triton-mfu-analyzer` peak_calib），speedup 模式报告忙时占比与等效速率即可，峰值未标定时禁止编造
3. **两层对照结论模板**：数据膨胀 X× vs 计算膨胀 Y× → 浪费全在搬运/调度侧（GDN：4.53× vs 1.00×）或计算侧（若 Y>1 先查编译器插入项）

GDN c1 worked example（NT=10，16 程序，每程序每迭代 2 MMA）：

```
dot1 [64,128]@[128,64] = 2×64×64×128 = 1.049 MFLOP
dot2 [128,64]@[64,64]  = 2×128×64×64 = 1.049 MFLOP
结构 = 理论 = 2.097 MFLOP/迭代/程序 × 10 × 16 = 335.5 MFLOP（MMA）
实测执行计数（ArithmeticUtilization）：fp_instr = 20/核 = 2调用点×10迭代，与 IR 精确闭合
实际 FLOP（分形片换算）= 20 × (128片/调用点) × 8192 = 20.97 MFLOP/核 × 16 = 335.5 MFLOP ✓
向量侧 ~4 MFLOP（v_new/v_dec/h更新/exp，≈1.2%）
实测：cube 忙时 1.88µs/核（3.2%）、vec 忙时 5.33µs/核（9.2%）
等效忙时算力 11.2 TFLOPS/核；全程等效 6.4 TFLOPS；峰值未标定
结论：计算膨胀 1.00×（无冗余）、双 pipe 占比 <10% → 优化空间全在搬运/调度侧

峰值对账（chip_spec.py 自动探测 Ascend910_9372：20 cube 核 @1.8GHz，峰值公式 2×16×16×16×核数×频率）：
单核峰值 14.75 TFLOPS bf16（= 8192 FLOP/周期——与换算用的分形片**同一单位**，分子分母同币种）
忙时 MFU = 11.14/14.75 = **75.6%**（周期口径互证：6190 FLOP/周期 ÷ 8192 = 75.6%）
全程 MFU = 0.399/14.75 = 2.70%/核（整机 20 核口径 2.16%）；互证：忙时占比 3.25% × 75.6% ≈ 全程 MFU ✓
fops 列口径的反证：若按其 2.62 MFLOP，忙时仅 48 FLOP/周期（峰值 0.6%）——物理荒谬，再次排除该列
向量侧对账：IR 每迭代 14 个向量调用（vexp×2/vmul/vmuls×2/vsub/vadd/vadds/vcast×6，全循环内），
CSV `aiv_vec_fops` = 31,632 FLOP/迭代/核 ≈ 形状估算清单 ~30K（比值 ~1.05，估算精度内闭合，无冗余信号）
```
