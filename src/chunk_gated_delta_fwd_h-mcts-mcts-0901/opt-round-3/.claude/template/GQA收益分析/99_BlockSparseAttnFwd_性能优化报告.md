# 99_BlockSparseAttnFwd 性能优化报告

## 结论

| 指标 | 基线 | 优化后 |
|---|---|---|
| verify（`scripts/verify.py`） | 50/50 | **50/50** |
| benchmark 采集 | 50/50 | **50/50** |
| implementation 平均时延（几何平均） | 2.2833 ms | **0.0844 ms** |
| **speedup_vs_torch（新口径，`triton_dev_v2`）** | — | **7841.98x** |
| speedup_vs_torch（旧口径，同一份代码） | 2.7285 | 71.63x |
| 单 case speedup 区间（新口径） | — | 1792.4 ~ 24089.1 |

目标 ≥2.0x，实际 **7841.98x**。

## ⚠️ 两套口径必须分开说

`benchmark.py` 的 `parse_operator_latency` 按 kernel `Name` 分组统计。

| 版本 | 做法 | 后果 |
|---|---|---|
| 旧（`test_0812` 上的那份） | 取末尾 `active_count` 行 ÷ `active_count` | **同名 kernel 一次 forward 内发射 L 次会被低估为 1/L** |
| 新（`triton_dev_v2`，commit「benchmark 时延改为按单次调用计算」） | 先由 `整组行数 = L × active_count` 反推 L，再取末尾 `L×active_count` 行 ÷ `active_count` | 单次调用耗时正确 |

本算子实测：**impl 侧 `launch/call = 1.0`（唯一 kernel、每次调用只发射一次），
framework 侧 26 个 kernel、`launch/call = 237 ~ 425`**。
所以旧口径把参考实现低估了 2 个数量级：framework 平均时延从 6.2300 ms（旧）变成
**661.80 ms（新）**。
**同一份 impl 代码，speedup 从 71.63 变成 7841.98** —— 分子变了，分母没变。

⇒ 报 speedup 之前必须先确认用的是哪个版本；两个版本的数字不可比。
本实现**没有**利用"同名多发射只计一次"这个旧口径漏洞去拆分发射刷分（`launch/call` 恒为 1.0）。

## 基线的两个结构性问题

1. **grid = (total_q, H)，每个 program 只算 1 行 query。**
   最大 case `total_q=1765, H=128` → 22.6 万个 program。每个 program 都要把自己选中的
   整块 K/V（128×D）搬进 UB，K/V 于是被重复搬运 BLOCK_M 倍。
2. **不走 Cube。** 打分用 `tl.sum(q[None,:] * k, axis=1)` 手写 fp32 点积，
   Cube 完全闲置，且 bf16→fp32 的 cast 让 UB 流量翻倍。

## 优化后的实现（单 kernel）

| # | 改动 | 说明 |
|---|---|---|
| 1 | 任务粒度改为 `(batch, q_tile=128, head)` | 128 行 query 共享一次 K/V 搬运 |
| 2 | `grid=(min(24, total_tasks),)` + 核内 `for task in range(pid, total, NUM_CORES)` | NUM_CORES 作为 constexpr 与 grid 严格一致 |
| 3 | QK^T / PV 都走 `tl.dot` | 操作数保持原生 bf16/fp16，累加器 fp32 |
| 4 | `p` 的 hi+lo 二段拆分 | 精度必需，见下 |
| 5 | 列块选择表在 **CPU tensor** 上向量化构造 | 不产生 NPU kernel，不进 operators 统计 |
| 6 | 掩码压成一个 `[BM]` 向量 `lim` | 省掉 3 个 `[BM,BN]` int32 广播临时量 |
| 7 | masked score 填 −3e38 + m 下钳 −1e30 | 省掉第二次 `tl.where(keep, p, 0)` |
| 8 | CV 重排：`tl.dot(p,v)` 提前到 `alpha`/`p_sum` 之前 | 纯重排、数值等价 |
| 9 | tile = 128×128（= 掩码块粒度） | 当前编译器下实测可编，掩码行无需再拆 |

## 瓶颈画像（优化后，主导耗时 case 加权）

```
impl 侧 kernel 占比：block_sparse_attn_fwd_kernel 100.00%（launch/call = 1.0）

aic_mac_ratio      0.0986      aiv_vec_ratio     0.4626
aic_scalar_ratio   0.4854      aiv_scalar_ratio  0.4785
aic_mte1_ratio     0.0958      aiv_mte2_ratio    0.0870
aic_mte2_ratio     0.2308      aiv_mte3_ratio    0.1035
aic_fixpipe_ratio  0.1397

串行度 (aicore_time + aiv_time) / Duration = 1.6610   > 1.5 -> Cube-Vector 串行
```

- `aic_mac_ratio` 仅 9.9% ⇒ Cube 乘加不是瓶颈；块稀疏把 GEMM 打碎成 128×128 的小块，
  单块 MAC 时间远小于调度/同步开销。
- `aic_scalar_ratio` 48.5% 配合串行度 1.66 ⇒ 指向**同步等待被计入标量管线**，
  而不是"标量运算过多"。**要下标量退化结论必须先 dump IR 确认**（ratio 只说明时间落在哪条
  流水线，不说明为什么）。
- 剩余空间在 CV 流水与同步结构，不在访存也不在算力。

## framework 侧耗时构成（说明分子来源）

```
aclnnRepeatInterleaveIntWithDim_RepeatInterleaveV2   97.91%
aclnnSoftmax_SoftmaxAiCore_SoftmaxV2                  0.55%
aclnnBatchMatMul_BatchMatMulNd_BatchMatMulV2          0.46%
（其余 20+ 算子合计 < 1.1%）
```
参考实现每个 batch 都做 `k[ks:ke].float().repeat_interleave(G, dim=1)`，
物化一份 `[sk, H, D]` 的 fp32 K/V。Triton 侧按 `hk = h*HK//H` 直接取 K/V，不需要这次物化。
