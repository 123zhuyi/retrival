# 极限 MFU 的测定：(case, 倍率) 二维搜索

## 先说定义：极限 MFU ≠ 最大 shape 下的 MFU

这是最容易犯、且后果最隐蔽的一个错误。

**MFU 对 shape 不单调。** 小 shape 时数据在 cache 里，放大后被打回 HBM，
`aic_mte2` 变成墙，MFU 反而下降。实测 62 个 Level4 算子里**约 2/3 放大后 MFU 降低**。
若把「最大 shape 下的 MFU」当成「极限 MFU」，会出现
**`极限 MFU` < 数据集原始 shape 下的 MFU** 这种自相矛盾的结果（实测 14/51 行）。

**极限 MFU = 在候选空间里取到的最大值**，候选空间是两个维度：

| 维度 | 为什么必须扫 |
|---|---|
| **倍率 s** | MFU 对 shape 不单调，峰值常在中间档而非最大档 |
| **case** | 同一算子的不同 case 可能走**不同的代码路径** |

case 这一维尤其容易漏。实测 `55_OutlookAttention`：

| case | dtype | FLOPs | MFU | 实际执行的 kernel |
|---|---|---|---|---|
| 11 | fp16 | 6.1e10 | **20.8%** | 只有 `_linear_kernel` |
| 38 | bf16 | 2.6e11 | 2.4% | `_linear/_pool/_softmax/_attn/_fold` 五个 |

case 11 的 MFU 高出 8 倍，因为实现里有 shape 相关的**早退路径**，它根本没做完整的
OutlookAttention。只固定"FLOPs 最大的 case"会系统性漏掉这类点；
反过来，报 case 11 的 20.8% 时也必须注明它只走了一个 kernel，否则等于拿退化路径充数。

## 两级搜索与参数标定

数据集每个算子约 50 个 case，全部逐点采集太贵（50 × 89 ≈ 4450 次 msprof）。分两级：

1. **初筛（墙钟，单进程遍历）**：候选池 = 按 FLOPs 降序的前 8 个**原始 case**
   + 它们通过合法性闸的**放大变体**。原始 case 无条件入池——只要它们在池里，
   `极限 MFU >= 原始 shape 下的 MFU` 就自动成立。
2. **精测（msprof）**：只对初筛前 3 名采集。**最终数字一律取自精测的 kernel 时间。**

### 为什么初筛池取 FLOPs 前 8

5 个算子全 50 case 实测标定，最高 MFU 的 case 在 FLOPs 降序里的位次：

| 算子 | 最高 MFU | 位次 | top-3 命中 | top-5 命中 |
|---|---|---|---|---|
| 13_ScaledDotProductAttention | 6.514% | **4** | ❌ | ✅ |
| 20_FlashAttentionV2 | 9.395% | 2 | ✅ | ✅ |
| 28_FlashAttentionFwd | 15.635% | **5** | ❌ | ✅ |
| 55_OutlookAttention | 18.388% | 3 | ✅ | ✅ |
| 66_LinearAttention | 0.779% | 2 | ✅ | ✅ |

**top-3 有 2/5 漏掉最高点，top-5 全部命中**；取 8 是在 top-5 上留冗余，
吸收墙钟排序可能的翻转。三种 dtype（fp16/bf16/fp32）都出现过冠军，
**不能只按 dtype 挑**。

### 墙钟开销：为什么初筛可用

同一 case 两种口径对照（op28，s=1）：

| case | 墙钟 ms | kernel ms | 差值 | 开销占墙钟 | MFU 低估 |
|---|---|---|---|---|---|
| 26 | 0.1439 | 0.0737 | 70.2 us | 48.7% | 48.8% |
| 33 | 0.1724 | 0.1436 | 28.8 us | 16.7% | 16.7% |
| 47 | 0.8879 | 0.8575 | 30.4 us | 3.4% | 3.4% |

**开销是每次前向 30~70us（均值 43us）的 host 侧固定成本，与 kernel 时长无关。**
所以低估幅度 = 开销/墙钟，完全由 kernel 时长决定：

```
kernel ~70us -> 低估 49%      ~140us -> 17%
kernel ~860us -> 3.4%          >2ms   -> <2%
```

危险区在 **kernel < 200us**，那里墙钟能把 MFU 压低近一半、足以颠倒排序。
但极限 MFU 几乎总出现在大 case 上（标定的 5 个冠军 kernel 时长都在毫秒量级），
**墙钟失真最严重的恰好是注定不会夺冠的小 case** —— 这是初筛可用的前提，
也是为什么不能把入围数压到 top-1。

## 为什么放大 shape 这一步不能省

benchmark 数据集里的用例是**正确性用例**，不是性能 shape。典型规模：

```
13_ScaledDotProductAttention  Q[2,3,7,16]  K[2,3,9,16]  V[2,3,9,16]
```

在这种 shape 上测出来的 MFU 只反映 kernel 启动开销，而且**测不出真实瓶颈**：
数据全在 cache 里，访存墙根本不显形。放大之后才看得见。

一批 Level4 算子放大前后的对比（94 个算子，62 个测得有效数据）：

| 现象 | 数据 |
|---|---|
| 放大后 MFU 提升的 | 约 1/3（最大 11 倍：MultiHeadLatentAttention 0.65% → 7.23%） |
| 放大后 MFU **下降**的 | 约 2/3 |
| 下降的原因 | 新出现的 bound 以 `aic_mte2` 为主，多个已达 0.9+（Linformer 0.983、BlockSparse 0.992） |

**下降才是有价值的信息**：小 shape 掩盖了 GM→L1 的搬运墙，放大后算子被打回 HBM，
这才是它在真实负载下的样子。

## 放大哪些维度：只放 seq_len 和 batch

**不要等比放大所有维度。** 两个原因：

1. **体积按 `s^ndim` 爆炸**。4D 张量 s=2 就是 16 倍显存，预算立刻见底，
   相邻倍率档能差 8 倍，粒度极粗。
2. **多数维度放大没有意义**。head_dim、heads 是模型架构定死的，
   放大它们得到的不是"同一个算子的更大规模"，而是一个不存在的模型配置。

**真正该放大的是 seq_len 和 batch**：

- `seq_len` —— attention 的 FLOPs 随它**二次**增长，而 KV 显存只**线性**增长
  （`[B,S,H,D]`）。这是提升算术强度、进而提升 MFU 的主要杠杆。
- `batch` —— 提高并行度，显存也是线性增长。

两者的体积代价都是线性的，同样的预算能探到远比等比放大更大的范围。

### 怎么认出哪些位置是 seq、哪些是 batch

**这一步要人工确认，不要写死在脚本里** —— 硬编码的维度识别一旦与实际语义不符，
会静默放大错维度，比不放大更糟。

数据集的几十个 case 提供了判断依据：**同一个符号的 `(张量名, 轴)` 位置，
在所有 case 上取值必然完全一致**。把每个位置在全部 case 上的取值向量拿出来分组，
就能还原维度的语义结构。实测 `28_FlashAttentionFwd` 的分组结果：

```
q.0, k.0, v.0  → batch      1~4
q.1            → seq_q      3~897
q.2            → q heads    2~64
k.1, v.1       → seq_k      9~921        ← 与 q.2 不同组，正确区分了 GQA
k.2, v.2       → kv heads   1~16
q.3, k.3, v.3  → head_dim   16~192
```

`13_ScaledDotProductAttention` 甚至能分出 `Q.3/K.3`（QK 的 head_dim）
与 `V.3`（V 的 head_dim）两个不同符号。

定位的两条经验规则（**仅供参考，需逐算子核对**）：

- **batch**：覆盖多数张量 axis-0 的那个符号。
- **seq**：其余符号里取值范围最大的，但**必须排除"每个张量的末轴"**——那通常是 head_dim。
  这条排除不能省：`20_FlashAttentionV2` 的末轴符号范围 48~1536，比 seq 的 897 还大；
  `3_FusionAttention` 的两个末轴符号（8~8192、8~4096）都远大于 seq（1~512）。
  只按"范围最大"选会全部选错。

`seq_q` 与 `seq_k` 常被识别成两个独立符号，可以分别放大，也可以同步放大
（保持因果 attention 的 `seq_k >= seq_q`）。

### 放大档位建议

```
batch × {2, 4, 8, 16, ...}
seq   × {2, 4, 8, 16, ...}
两者组合 × {2, 4, 8, ...}
```

## 五道闸，缺一不可

按代价从低到高排列，先便宜的挡掉，能省大量卡时。

### 闸 1：输入字节预算

`case_bytes(base, s) <= --max-bytes`（默认 10 GB）。纯计算，零成本。

### 闸 2：参考实现必须接受该 shape

**这是最容易漏掉、后果最严重的一道。**

判据：对参考实现 `class Model` 做 FakeTensor 追踪成功且 FLOPs > 0。

> **这一步不是无条件便宜的，会爆内存。** FakeTensor 成功时几乎零开销；
> 但 tracer 通常带「fake 失败则回退真实张量」的路径，而参考实现里
> `scores = q @ k^T` 会**实例化 `[B,H,Sq,Sk]` 的稠密中间张量**。
>
> 只按输入规模设阈值挡不住 —— **护栏检查的是输入，爆的是中间量**：
> `Sq=Sk=8192`、40 heads 时输入仅约 100 MB（轻松通过 3e8 元素的阈值），
> 而 score 矩阵是 `40×8192×8192 = 2.7e9` 元素 ×4B = **10.7 GB**。
>
> **对策：FakeTensor 失败即跳过，不回退真实张量。**
> 真实张量算出的 FLOPs 与 fake 一致，回退没有任何收益，只有爆内存的风险。
> 追踪子进程会带 `MFU_FLOPS_NO_REAL=1`（供 tracer 自行遵守），
> 并设 `RLIMIT_AS` 硬上限兜底（对不认该变量的 tracer 同样有效，
> 默认 8 GB，`--flops-mem-cap-gb` 可调）。跳过的点按「参考实现拒绝该 shape」处理。

漏掉它的后果：`ModelNew` "能跑"不代表结果有意义。实测中 26 个算子出现过
参考实现拒绝而被测实现照跑的情况：

```
60_SKAttention               RuntimeError: Given groups=1, weight of size [5...
40_ChunkKdaWithFusedGateFwd  RuntimeError: shape '[1,3838,21,168]' is invalid
14_WindowAttention           RuntimeError: mat1 and mat2 shapes cannot be multiplied
```

等比缩放破坏了参考实现里的形状约束（卷积权重尺寸、固定 reshape 等）。
参考实现拒绝的输入，语义上就不合法，同时 FLOPs 也算不出来——分子没了，MFU 无从谈起。

### 闸 3：被测实现在 device 上跑通

常见失败：MLIR 编译错误、UB 溢出、算子自身的断言。这些是真实的承载上限，如实记录。

### 闸 4：单次前向耗时上限

`ms <= --max-ms`（默认 4 s）。再大 PMU 采集不现实（开 PMU 后耗时会放大 2~16 倍）。

> **注意实现细节**：超时限的点**不能被采纳为 best**。
> 「先记录 best 再 break」会把超时的配置当成结果——实测中有算子因此收了个 11.5 s 的点。
> 正确做法是判定超限后直接回退到上一个可行档。

### 闸 5：物理合理性（有效带宽 <= HBM 峰值）

```
bw = 输入字节 / 单次耗时   必须 <= 1.3 TB/s（910B2C）
```

超过 HBM 峰值说明 **kernel 根本没有消费这些输入**，缩放没生效。

这道闸是**兜底**——它能挡住所有"我没预料到的失效方式"，不需要逐个算子去猜。
实测中它一次性暴露了 89 个算子里 55 个的失效（详见下一节的坑 1）。

## 已知的坑

### 坑 1：用例文件名各算子不统一（静默失效，最隐蔽）

各算子 `model.py` 读用例的方式不一样：

```python
# 有的这样（读 model.json）
json_path = os.path.splitext(__file__)[0] + ".json"

# 有的硬编码
json_path = os.path.join(os.path.dirname(__file__), "43_CoordAtt.json")
```

只写其中一个，后一类算子会**继续跑原始小 shape**，而且完全不报错。

症状：**耗时不随数据增长**。实测 43_CoordAtt 数据 ×6561、耗时 ×1.06，
"有效带宽" 22.8 TB/s——是 HBM 的 17 倍。

对策：`case_files()` 把 scaled case 写进目录下**所有**候选用例文件。
闸 5 是这个坑的安全网。

**反过来也要防**：写入前必须排除流程产物，否则会覆盖掉别人的结果。
判定用两道——先按文件名排除 `verify_result*.json`（精度校验）、`perf_result*.json`（性能结果）
等已知产物，再按内容确认（每行是含 `inputs` 列表的对象）。
只靠内容不稳（产物结构会变），只靠文件名也不够（下个批次会多出新产物）。

### 坑 2：attr 锁死张量维度

有些算子的真实计算量由 attr 决定，不由张量 shape 决定。等比放大张量而不动 attr，
要么触发断言，要么分配了大 buffer 却只算一小部分。

```
77_TrtllmBatchDecodeWithKvCacheMla
   kv_cache[259, 64, 576]        kv_lora_rank=512 + qk_rope_head_dim=64 = 576  ← 锁死最后一维
   query[16, 1, 4, 576]          kv_lens=[1024]*16  block_tables[16,16]        ← 锁死 batch
```

放大到 s=1.5 直接 `AssertionError`。这类算子的真实上限就是 s=1。

要真正放大必须让 attr 联动：列表型 attr 按新 batch 重复填充；标量 attr 若等于某张量维则同比放大；
若干 int attr 之和等于某维时按比例分配并让最大的吸收取整误差。
但这等于换了一个更大的模型配置，是否还算"同一个算子"需要先和需求方确认。

### 坑 3：混合实现不能只统计 triton kernel

很多 `ModelNew` 是 **triton kernel + torch/aclnn 算子**的混合实现。
如果按 `Op Name.startswith("aclnn")` 过滤掉框架算子，分子算的是整个算子、
分母只算 triton 那部分，MFU 会虚高。

实测 26_ViTAttention 因此得到 **102.9%**——超过 90.4% 的物理上限。

对策：按 `Task Start Time(us)` 排序后做**周期检测**，取最后 N 个周期。
前向的算子序列会以固定周期重复（warmup + 计时迭代），
setup 阶段的输入生成算子（ZerosLike / Uniform）自然被排除，混合实现的 torch 算子被正确计入。

```python
def period(names, n_iters):
    N = len(names)
    for m in range(n_iters, 2, -1):
        for p in range(N // m, 0, -1):
            tail = names[N - m * p:]
            if all(tail[i * p:(i + 1) * p] == tail[:p] for i in range(m)):
                return p, m
    return None, None
```

### 坑 4：采集残缺时必须拒绝出数

算子在探测阶段跑通，加上 PMU 后仍可能崩（aicore 异常 507015）。
若只采到 1 次前向却仍按 N 次迭代平均，kernel 时间会小 N 倍、MFU 大 N 倍。

对策：runner 跑完打印哨兵行（如 `[RUN] ok`），汇总时校验其存在；
不存在则**不出 MFU**，并在结果里写明"采集残缺"。

### 坑 5：PMU 比值可能 > 1

流水占比本应 ≤ 1。实测 1233 行里有 1 个算子（45_CrossformerAttention）的
5 个 `aic_*` 项同时 > 1（`aic_mte2` 加权到 3.170），是该 MIX kernel 的
`aicore_time` 相对各核实际忙时被低估，计数不自洽。

对策：任一原始比值 > 1.05 时，标记该算子"PMU 计数不自洽"，**不做 bound 判定**，
不要拿它冒充一个饱和的流水。

---

### 坑 6：把"最大 shape 下的 MFU"当成"极限 MFU"

自检判据很简单：**`极限 MFU` 必须 >= 同一算子在原始数据集 shape 下的 MFU**。
出现反例就说明候选空间没扫够（漏了 case 维、或峰值落在中间倍率）。

实测这条判据一次性揪出 14/51 行的问题。把 `s=1` 与原始 top-3 case 一并放进候选集后，
该不等式自然成立——因为旧口径测的那个点本身就在候选集里。

## 结果里应该记录什么

每个算子至少记这几项，缺了就无法追溯：

| 字段 | 说明 |
|---|---|
| `shape口径` | 通过了哪几道闸。区分「双验证」（参考+被测都通过）与「仅被测通过」 |
| `s` / `dev_s` | 采用的倍率；若因参考实现拒绝而回退，同时记设备能跑到的倍率 |
| 实际 shape | 放大后各张量的具体维度 |
| `有效带宽` | 用于事后复核闸 5 |
| `stop` | 上界卡在哪一道闸、什么错误 |
| **取到极限的 (case, s)** | 极限 MFU 在哪个点取到，便于复现与质疑 |
| **该点执行了哪些 kernel** | 若只跑了一个 kernel，要警惕是早退路径而非完整算子 |

**无法出数的行不要留空**，写明原因，否则和"还没测"分不清。
